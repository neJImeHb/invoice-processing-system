## Інваріанти

Тест не можна підганяти так, щоб він пробачав злам одного з цих пунктів.

1. **Одна функція переходу.** Кожна зміна статусу, включно з повтором, іде через неї. Оновлення має вигляд `WHERE id = $1 AND status = $2`, виставляє `updated_at`, і лише потім публікує SSE. Нуль рядків означає, що викликач програв гонку. SSE в цьому випадку немає.
2. **Одна функція повтору.** Її викликають і `POST /api/invoices/:id/retry`, і `retry_failed_invoice`.
3. **Термінальний запис — одна транзакція.** `extracted_data`, `normalized_text`, заміна чанків цього інвойсу і `status = completed` комітяться разом. `failed` комітиться з `error_message` і без чанків. Функція переходу приймає той самий `PoolClient`, що й запис чанків.
4. **Зсув Kafka йде після бази.** `autoCommit: false`. Комітити зсув після коміту тієї транзакції.
5. **Повторна доставка безпечна.** `completed` або `failed`: закомітити зсув і зупинитися. `processing` без `extracted_data`: витягати знову. Рядка немає: закомітити зсув і зупинитися. Успішна транзакція видаляє чанки цього інвойсу і вставляє новий набір. Воркер, який закінчив після видалення, оновлює нуль рядків і комітить зсув.
6. **Невдале публікування компенсується.** Порядок завантаження: записати файл, вставити `uploaded`, опублікувати, надіслати SSE, повернути 202. Якщо публікація кидає виняток, видалити рядок і файл і повернути 503.
7. **Модель не пише SQL.** Інструмент статистики має один фіксований запит і зв'язані параметри.
8. **Файли лишаються під коренем uploads.** Завантаження розв'язує збережений шлях і перевіряє, що справжній шлях усередині каталогу. Ім'я на диску — `<uuid>.<ext>`. `original_name` лише для показу і не містить роздільника шляху.
9. **Секрети лишаються на сервері.** Браузер ніколи не отримує `GEMINI_API_KEY`.
10. **Старт відмовляється без конфігурації.** Відсутні `GEMINI_API_KEY`, `DATABASE_URL` або `KAFKA_BROKERS` кидають виняток до `listen`. Тести піднімають `createApp` з фейками. Усередині екстрактора, споживача і маршрутів немає гілки `if (NODE_ENV === "test")`.
11. **Розмір файлів.** Нові файли TypeScript — до 200 рядків. Функції — до 50.

### Переходи статусів

| Звідки | Куди | Хто |
|---|---|---|
| — | `uploaded` | Вставка під час завантаження. Не функція переходу. |
| `uploaded` | `processing` | Воркер, до виклику моделі |
| `processing` | `completed` | Воркер, усередині успішної транзакції |
| `processing` | `failed` | Воркер, з конкретним `error_message` |
| `failed` | `uploaded` | Лише функція повтору. Очищає `error_message`, збільшує `retry_count`, публікує нову подію |

Будь-яка інша зміна оновлює нуль рядків. Видалення дозволене з кожного статусу.

Повтор інвойсу, який не в `failed`, повертає HTTP 409 `{ "error": "invoice_not_failed", "status": "<поточний>" }`. Невідомий id повертає 404 `{ "error": "not_found" }`. Інструмент повертає той самий результат і не кидає виняток повз граф.

## Припущення, записані тут

План їх дозволяє і не обирає значення. Затвердження цього файлу їх приймає.

| Тема | Вибір |
|---|---|
| Поганий тип файлу | Порожнє тіло — 400. Розбіжність заявленого типу, розширення або сигнатури — 415. Понад 20 МБ — 413. |
| Межа розміру | Байти рахує застосунок. `<= 20 * 1024 * 1024` приймається. Особливість рівності в multer не є авторитетом. |
| Де лежать байти до прийняття | Пам'ять multer 2. Каталог uploads отримує файл лише після перевірки сигнатури. |
| Раннер тестів | Vitest для юнітів і інтеграції. Playwright для браузера. |
| Скрипт e2e чату | `npm run test:e2e:chat`, і `npm run verify` його запускає. |
| Невірний `threadId` | 400 `{ "error": "invalid_thread_id" }`. Відсутній `threadId` створюється. |
| Порожнє повідомлення чату | 400 `{ "error": "empty_message" }`. |
| Публікація повтору не вдалась | Та сама ідея, що в інваріанті 6. Якщо публікація кидає виняток після оновлення повтору, повернути `failed`, попередній `error_message` і попередній `retry_count`, і віддати 503 `{ "error": "broker_unavailable" }`. Інструмент повертає цей результат і не кидає виняток повз граф. |
| Тіло відповіді, коли брокер лежить під час завантаження | 503 `{ "error": "broker_unavailable" }`. |

**Як** перевіряльник

5. Додати пул `pg` з `DATABASE_URL`. Запити параметризовані. Здоров'я викликає `SELECT 1`.

### US-003: Зберегти перевірений файл і віддати його назад

**Як** користувач  
**я хочу** завантажити PDF або зображення і пізніше відкрити чи видалити його  
**щоб** оригінал лишався доступним, а поганий файл ніколи не ставав рядком

**Сліди:** план CP-2, історія 1. Підтримує AS-001. Залежить від US-002.

**Кроки:**

1. Додати `server/src/services/storage.ts`. `saveAcceptedFile` пише `<uuid>.<ext>` під коренем uploads. `remove` видаляє цей файл. `openInsideUploads` розв'язує справжній шлях і кидає виняток, якщо він не всередині кореня. Перевіряти справжній шлях, не рядковий префікс, щоб `..` і символічні посилання не виходили назовні.
2. Магічні байти, після multer, до запису:
   - `application/pdf` починається з `%PDF`
   - `image/png` починається з `89 50 4E 47 0D 0A 1A 0A`
   - `image/jpeg` починається з `FF D8 FF`
3. Заявлений тип частини і сигнатура мають зійтися. `image/jpg` відхиляється. Розширення збереженого імені береться з сигнатури (`.pdf`, `.png`, `.jpg`), не з імені клієнта.
4. `original_name`, який зберігається і повертається, — базове ім'я. Каталоги відрізати. Якщо ім'я порожнє, використати `invoice` плюс розширення. У збереженому значенні немає `/` і немає `\`.
5. Межі: немає файлу або порожнє тіло → 400. Розбіжність типу чи сигнатури → 415. Довжина більша за `20 * 1024 * 1024` → 413. Кожен із цих випадків не залишає ні рядка, ні файлу. Multer — `memoryStorage`, версія 2.x, змонтований лише на `POST /api/invoices/upload`. `express.static` для `uploads/` не додавати.
6. Вставити рядок зі статусом `uploaded`, ім'ям на диску, іменем для показу, mime, розміром і шляхом. Це єдина зміна статусу, яка не йде через функцію переходу.
7. Прийняти порт публікатора в `createApp`. Тести цієї історії використовують фейковий публікатор і записують корисне навантаження. Справжній продюсер KafkaJS — це US-004. Викликати порт об'єктом §4.4 і ключем `invoiceId`. `originalName` у нього не класти.
8. Маршрути:
   - `POST /api/invoices/upload` → 202 `{ id, filename, status: "uploaded" }`. `filename` — ім'я для показу.
   - `GET /api/invoices` з `status`, `limit` (типово 50, максимум 100), `offset` (типово 0).
   - `GET /api/invoices/:id` → `{ invoice, chunksCount }`. `chunksCount` дорівнює 0 до CP-3.
   - `GET /api/invoices/:id/file` віддає байти зі збереженим mime.
   - `DELETE /api/invoices/:id` видаляє рядок (чанки зникають каскадом) і файл.
9. Невідомий id на get, file і delete — це 404 `{ "error": "not_found" }`.
10. Тест замкненого шляху: рядок, чий шлях вказує поза uploads або містить `..`, не віддає ці байти. Обробник повертає 404 або 400 і не читає файл поза коренем.

**Критерії прийняття:**

- [ ] Малі PDF, PNG і JPEG кожен повертають 202, рядок у `uploaded` і файл `<uuid>.<ext>`
- [ ] `filename` у тілі 202 — ім'я для показу, і в ньому немає роздільника шляху, навіть якщо клієнт його надіслав
- [ ] Порожнє тіло → 400. HTML, перейменований на `.pdf`, або байти PDF, заявлені як `image/png` → 415, без рядка і без файлу
- [ ] 20 МБ + 1 байт → 413, без рядка і без файлу. Файл рівно на 20 МБ валідних байтів PDF приймається
- [ ] Список фільтрує за `status` і дотримується `limit` та `offset`, включно з типовими значеннями і максимумом 100
- [ ] `GET /api/invoices/:id` повертає `chunksCount: 0`
- [ ] GET файлу повертає ті самі байти і збережений content type
- [ ] Видалення прибирає рядок і файл
- [ ] Тест замкнення не читає файл поза `uploads/`
- [ ] Жоден тест цієї історії не викликає Google

### US-004: Поставити завдання в чергу і сказати відкритим браузерам

**Як** користувач  
**я хочу**, щоб завантаження потрапило в чергу, і кожна відкрита вкладка це побачила без оновлення  
**щоб** закритий ноутбук не губив завдання, а мертвий брокер не залишав рядок, який ніколи не виконається

**Сліди:** план CP-2, історія 2. Підтримує AS-001. Залежить від US-003.

**Кроки:**

1. Реалізувати продюсер KafkaJS у `server/src/kafka/producer.ts`. Публікувати `PROCESS_INVOICE` в `invoice-jobs` з ключем `invoiceId` і корисним навантаженням зі специфікації §4.4. `eventId` — новий UUID. `timestamp` — ISO-8601.
2. Порядок завантаження після перевірки US-003: записати файл, вставити `uploaded`, опублікувати, надіслати SSE, повернути 202. Якщо публікація кидає виняток, видалити рядок і файл, потім повернути 503 `{ "error": "broker_unavailable" }`. Не слати SSE для рядка, який потім видаляється. Не повертати 202.

```
event: INVOICE_STATUS_CHANGED
id: <монотонний id>
data: {"invoiceId","status","errorMessage","updatedAt"}
```

```
event: INVOICE_DELETED
data: {"invoiceId"}
```

6. Монотонний id зростає всередині процесу. `errorMessage` дорівнює null, коли помилки немає. `updatedAt` — це `updated_at` рядка після запису.
7. Інтеграційний тест: клієнт SSE отримує `INVOICE_STATUS_CHANGED` для нового id без опитування. Другий клієнт отримує `INVOICE_DELETED`, коли цей id видаляють.
8. Тестовий споживач у окремій тестовій групі читає запис і перевіряє тип, ключ і відсутність `originalName`.
9. Тест компенсації: двійник продюсера, який кидає виняток, не залишає ні рядка, ні файлу і повертає 503.
10. Vite не входить у цю історію. Тест говорить HTTP з `createApp`.

**Критерії прийняття:**

- [ ] За 202 іде рівно один запис у `invoice-jobs`, ключ = id інвойсу, тип `PROCESS_INVOICE`, поля рівно з набору §4.4
- [ ] Клієнт SSE бачить `INVOICE_STATUS_CHANGED` зі `status: "uploaded"` без перезавантаження сторінки
- [ ] Заголовки потоку — три названі вище, і коментар приходить протягом 20 секунд
- [ ] Невдала публікація повертає 503 і не залишає ні рядка, ні файлу
- [ ] Видалення надсилає `INVOICE_DELETED`, і файлу більше немає
- [ ] Виклику Gemini немає

### US-005: Один конвеєр від uploaded до completed

**Як** користувач  
**я хочу**, щоб інвойс у черзі став completed, з текстом, який пізніше можна шукати  
**щоб** статус на екрані збігався зі закоміченим рядком і закоміченим вектором

**Сліди:** план CP-3, історія 1. Підтримує AS-001. Залежить від US-004.

**Кроки:**

1. Додати `transitionInvoice(client, id, from, to, patch)`. Вона виконує `UPDATE ... WHERE id = $1 AND status = $2` і повертає рядок або нічого, коли змінилось нуль рядків. Сама SSE не шле. Викликач шле SSE лише після поверненого рядка, з його `updated_at`.
2. Додати чанкер. Токен рахується як 4 символи: розмір чанка 2000 символів, перекриття 200. Якщо перенос рядка стоїть у межах 200 символів до розрізу, рвати там. Рядок коротший або рівний 2000 символів — один чанк. Порожній чанк не віддавати. Перекриття не має створювати цикл.
3. Додати `prefixDocument(title, chunk)` і `prefixQuery(query)` в одному модулі. Форма документа: `title: {title} | text: {chunk}`. Назва — ім'я постачальника, інакше оригінальне ім'я файлу, інакше `none`. Форма запиту: `task: question answering | query: {query}`. `chunk_content` зберігається без префікса. Помічник запиту знадобиться в CP-7; визначити його зараз, щоб копія була одна.
4. Екстрактор і ембедер — інтерфейси. `test-server.ts` підставляє фейки. `index.ts` не підставляє їх до CP-6. Фейковий екстрактор повертає фіксований об'єкт, який проходить Zod-схему зі специфікації §4.5, включно з `normalizedText`. Фейковий ембедер — чиста функція префіксованого тексту і повертає одиничний вектор на 768 вимірів. Той самий текст дає той самий вектор. Інший текст дає інший вектор. Нульового вектора немає.
5. Група `invoice-processing-workers`, `autoCommit: false`, одне повідомлення за раз. Розібрати корисне навантаження через Zod. Для `uploaded` перейти в `processing`, надіслати SSE, потім запустити конвеєр.
6. Конвеєр: перевірка зашифрованого PDF і нечитабельного файлу (тексти помилок заповнює US-006; ця історія викликає ті функції), потім екстрактор, потім чанкер по `normalizedText`, потім ембедер один раз на чанк, потім одна транзакція: записати `extracted_data` і `normalized_text`, видалити чанки цього інвойсу, вставити нові, перейти `processing` → `completed` з `completed_at`. Закомітити. Потім закомітити зсув Kafka. Потім SSE `completed`.
7. Вставка чанка містить `chunk_index`, `chunk_content`, `embedding` і метадані `{ vendor, invoiceNumber, totalAmount, date }` з витягнутого об'єкта. Колонка ембединга — `vector(768)`.
8. Юніт-тести чанкера: короткий текст → один чанк; довгий текст → перекриття 200 і розріз на переносі, коли він поруч; порожніх рядків немає.
9. Інтеграційний тест на тестовому сервері: завантажити, дочекатися SSE `processing`, потім `completed`, прочитати рядок, перевірити один або більше чанків, довжину кожного ембединга 768, і що `chunksCount` у `GET /api/invoices/:id` збігається. Виклику Google немає.
10. Кожен новий файл — до 200 рядків. Конвеєр, споживач і SQL не ділять файл, якщо це перетне межу.

**Критерії прийняття:**

- [ ] Статус іде `uploaded` → `processing` → `completed` з двома подіями SSE, без опитування
- [ ] `extracted_data`, `normalized_text`, чанки і `completed` видимі разом. Примусова помилка всередині транзакції залишає рядок не в `completed` і не залишає зайвих чанків

- [ ] Тести чанкера покривають короткий інвойс, перекриття, розріз на переносі і заборону порожнього чанка
- [ ] Вектори фейкового ембедера мають довжину 768 і норму 1

### US-006: Збій, отруйне повідомлення, повторна доставка, heartbeat

**Як** користувач  
**я хочу**, щоб поганий файл став failed, а повторене повідомлення не псувало добре  
**щоб** у повтору була справжня точка старту, а падіння не дублювало вектори

**Сліди:** план CP-3, історія 2. Підтримує AS-001 і AS-002. Залежить від US-005.

**Кроки:**

1. До екстрактора просканувати байти PDF на ASCII-маркер `/Encrypt`. Якщо він є, екстрактор не викликати. Перейти `processing` → `failed` з `error_message`, який каже, що файл зашифрований. Закомітити це, закомітити зсув, надіслати SSE.
2. Файл, який воркер не може прочитати (немає на диску, порожній або обрізаний після сигнатури), стає `failed` з `error_message`, який каже, що файл нечитабельний. Ті самі правила коміту і зсуву. Екстрактор не викликати.
3. Екстрактор або ембедер кидає виняток, або Zod відхиляє JSON моделі: `failed` з текстом цієї помилки, без чанків, зсув закомічено, SSE надіслано. Розбіжність суми рядків і загального підсумку не є збоєм.
4. Отруйне повідомлення: повідомлення Kafka не проходить Zod схеми події. Залогувати, закомітити зсув, продовжити. Споживача не валити. Рядок не писати.
5. Повторна доставка, коли статус `completed` або `failed`: не викликати екстрактор, не вставляти чанки, закомітити зсув. Інтеграційний тест публікує те саме повідомлення двічі і перевіряє, що фейковий екстрактор викликано один раз.
6. Повторна доставка, коли статус `processing` і `extracted_data` дорівнює null: витягати знову. Успішна транзакція все одно спочатку видаляє наявні чанки.
7. Рядка інвойсу немає: закомітити зсув і зупинитися.
8. Видалити рядок, поки повільний фейк ще працює. Оновлення завершення збігається з нулем рядків, чанки не з'являються знову, зсув усе одно комітиться.
9. Heartbeat: споживач викликає `heartbeat()` обробника з інтервалом, коротшим за `heartbeatInterval`, поки екстрактор працює. `sessionTimeout` дорівнює 45000. Не ставити його на хвилини. Фейк тесту затримується близько 2 секунд і перевіряє, що `heartbeat` викликано принаймні раз. Інтервал — менше 1 секунди, щоб перевірка не залежала від типових 3 секунд брокера.
10. Юніт-тести: детектор шифрування знаходить `/Encrypt` і не чіпає звичайний крихітний PDF; гілка нечитабельного файлу не викликає екстрактор.

**Критерії прийняття:**

- [ ] Зашифрований фікстур → `failed`, повідомлення каже про шифрування, лічильник викликів екстрактора 0, SSE показує `failed`
- [ ] Обрізаний фікстур → `failed`, повідомлення каже, що файл нечитабельний, лічильник викликів екстрактора 0
- [ ] Екстрактор, що кидає виняток → `failed`, `error_message` заданий, чанків нуль
- [ ] Отруйне повідомлення закомічене, і споживач ще працює для наступного правильного повідомлення
- [ ] Друга доставка після `completed` не викликає екстрактор і не додає чанків
- [ ] Завершення після видалення оновлює нуль рядків і комітить зсув
- [ ] Повільний фейк бачить виклик `heartbeat()`
- [ ] `npm run test:integration:pipeline` покриває ці випадки і лишається в `npm run verify`

**Ймовірні файли:**

- `server/src/services/pdf-guard.ts`, `server/src/services/pdf-guard.test.ts`
- `server/src/services/pipeline.ts`

- `server/test/pipeline.integration.test.ts`

**Перевірка:** `npm run test:integration:pipeline`

**Як** користувач
